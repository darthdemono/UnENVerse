## 2. Decisions, with the alternatives rejected

1. **Node identity = Ed25519 request signing, not client certificates.** The design said "mutual fingerprint pinning". A custom `ClientCertVerifier` plus extracting the peer certificate inside handlers behind `axum-server`'s rustls acceptor is the largest, least testable part of the phase. Signing gives the same property (the hub pins the node's key; the node pins the hub's certificate) and is testable with `oneshot`. Cost: the hub's listener still accepts TLS 1.2 (it also serves the app and the CLI); only the node client refuses to negotiate down. Written in ADR-0140.
2. **Replay protection = strictly increasing timestamp, persisted**, plus a ±60 s window. Rejected: a nonce cache (memory, restart-sensitive). The mark lives in `nodes.json`, so a restart does not reopen the window (test `the_replay_mark_survives_a_restart`).
3. **Signature checked first.** Skew, replay and revocation are only reported to someone holding the key. Every failure is the same 401 text for an unknown node and a bad signature.
4. **Enrollment token binds the node's name and its projects.** The node cannot name itself or widen its scope by declaring a target; the hub intersects. Rejected: letting the node declare projects (a compromised node could ask for payroll).
5. **The hub stores no rendered content.** The design's own invariant would be hollow if `nodes.json` (unencrypted) held a `wg0.conf`. Hashes and status only; a pull passes through memory ≤120 s, once (tests assert the registry file contains neither `PrivateKey` nor the base64 of the content).
6. **Pull delivers a file to the owner; it does not parse it into chunks.** The parsers are TypeScript (`chunks/parsers.ts`); a Rust twin is a separate design. `accept` records the hash so the target reads `in_sync` until it changes. Recorded as not built.
7. **`listen` dialing deferred to 34.1.** It needs a hub-side scheduler and a hub signing key the node pins. The protocol is symmetric enough to add it without changing the wire types.
8. **The hub renders with the CLI's exporters**, so `envv-server` depends on the `envv-cli` library. Rejected: moving `exporters.rs`+`refs.rs`+`envfile.rs`+`out.rs` into `vault-core` (3k+ lines and a redaction global, for no behavioural gain). Cost: a bigger server build and the Dockerfile change.
9. **Config-check gate on the hub.** `render_gated` refuses a project whose `config_check` has an _error_ finding (e.g. two WireGuard peers with the same AllowedIPs); warnings do not block. This is the hook Phase 29.1 described (`config_check::gate`), done at the call site instead of as a new function; 29.1 can lift it into `vault-core` later.
10. **Heartbeats never touch the audit chain**; applies, tokens, enrollments, revocations, pulls and accepts do. Apply results ride the next beat and are cleared by the node only on `results_ack` (a locked hub cannot append to the chain, so it says `false`).
11. **Plain HTTP is refused by the agent except to the loopback.** A signature authenticates a request, it does not hide it, and a push carries secrets. Tests use loopback.
12. **`apply` on a push target is read only from the node's own config.** The hub learns it from the beat (to decide whether to send content) but cannot change it; the node re-checks inside `nodes_apply::apply` and refuses.
13. **Opt-in `--nodes`.** Off means 404 on every route and no `nodes.json` (tested).

## 5. Not done (named, so nobody assumes)

- `listen` mode; pull-into-chunks; per-beat render cache (every beat loads the vault and renders; fine at tens of nodes, measure before hundreds; the ceiling is O(vault) per beat per node).
- `node.apply` rows carry the node's reported error text (cut to 400 characters, scrubbed on the node). A hostile node can still write misleading text into its own audit rows; it cannot forge another node's actor.
- The hub trusts a node's `HostInfo`/`TargetReport` for display only; none of it feeds a decision except `apply` (which only controls whether content is sent, and the node re-checks).
- No rate limit on a signed node's beats beyond the per-IP failure limiter (a valid node can beat as fast as it likes). Add one if nodes are ever less trusted than "the operator's own machines".
- Phase 39 (pentest) should cover: enrollment token guessing and the 12-attempt limiter, replay across restart, the signature input format, the config-check gate bypass by project-name tricks, command injection through `reload` (only the node's own file feeds it), and the long-poll as a resource-holding route.

## 6. Traps for the next agent

- `envv-server` now depends on `envv-cli`. A new `include_str!` in `envv-cli` outside an already-copied path breaks the Docker image and nothing local notices (see phase log 50).
- Anything added to the beat payload must be added to both ends and to the `Beat` defaults, or an older node's beat fails to parse (`events`, `results`, `wait_secs` use `#[serde(default)]` for exactly this).
- `NodeStore::authenticate` persists `last_ts_ms` on every accepted request; do not call it twice for one request.
- `record_beat` replaces the node's target list wholesale each beat but preserves `accepted_sha` by target id.
- `nodes_wake.notify_waiters()` wakes only waiters already registered; the beat handler registers (`enable()`) **before** planning for that reason.
- The agent's `tls::configure` writes a process-global policy. One process, one hub; do not enroll two hubs from one process.
- Prettier is off for embedded languages; do not run it over `html` template files you did not write.
