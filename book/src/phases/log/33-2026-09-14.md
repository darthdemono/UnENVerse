## The bugs that mattered

Ranked by consequence to the user, not by size of the fix.

1. **A1 - every 2FA code was blank on every remote vault.** The gate checked
   whether the _local_ SQLCipher key was present, which is `None` on a
   session connected only to a remote - the same bug shape as the Phase 12
   LAN wrong-vault fix, three years and several phases later, in a different
   command. Nobody was told why; the slot just showed `- - -` forever.
2. **A3 - every export in the app reported success and wrote nothing.**
   WebKitGTK's webview has no download handler and the app has no dialog/fs
   plugin, so a `<a download>` click silently went nowhere while the toast
   said "Exported ✓". This covered ICS, `.env`, YAML, JSON, k8s Secrets,
   `.tfvars`, encrypted backups, settings export and the bulk `export.env`
   tool - nine call sites, all fixed by the same helper.
3. **A11 - an entry of an unrecognised type would have been silently
   downgraded to `api_key` on the next Save**, once 24.1 or 24.5 ships a type
   this build predates. Not yet reachable in the wild (no build has shipped
   `composite` before this session), which is exactly why it had to land
   _first_ - the design's own point about A11 needing to be released before
   the type that would trigger it.
4. **A2 - two surfaces for one feature, one of them silently broken.** The
   sidebar Authenticator section showed nothing whenever A1's bug applied,
   and having two places to look for the same six digits is confusing even
   when both work. Removed rather than fixed twice.

## Decisions made

- **RFC 3986's unreserved set is hand-rolled in both languages, not
  delegated to `encodeURIComponent`.** JS's built-in additionally leaves
  `! ~ * ' ( )` unescaped; using it in TypeScript while Rust used a strict
  RFC 3986 encoder would have made the twin pair disagree on exactly the
  inputs a security-relevant fixture would think to test.
- **Composite zone classification reads the template's own text, never the
  rendered output.** Parsing a URL built from the actual secret values would
  mean the classifier's input already contains whatever ambiguity (an `@` in
  a password, a `/` in a token) the classification exists to resolve
  correctly. The template's structure is fixed and known before any part is
  filled in.
- **No save-dialog plugin for A3.** Adding `tauri-plugin-dialog` is a real
  dependency and capability-file change for a defect fix; the downloads
  directory plus filename disambiguation gives the correct behaviour (a real
  file, never silently overwritten) without it. Worth reconsidering if a
  "Save As…" UX is explicitly requested later.
- **`bundle` was added as a `SecretType` and field set this session, with
  nothing built on top of it, rather than left out of the union entirely.**
  The alternative was leaving `TYPE_CONFIG`'s `Record<SecretType, TypeConfig>`
  un-exhaustive until step 3 lands, which means the type wouldn't typecheck
  the moment anything else touches that map. Landing the shape now and the
  behaviour later is the same call E4 made about `formToEntry`'s spread.

## What Worked / What Didn't Work

**Worked:**

- Following each phase's own "Order of work" list literally, front to back,
  rather than picking items by perceived interest - it is already priority-
  ordered with the dependencies worked out.
- Writing the Rust and TypeScript composite renderers side by side, function
  by function, rather than one and then the other - the zone classifier in
  particular would have been easy to get subtly wrong in the second language
  if it were translated from a finished first draft instead of built in
  parallel with the same test cases in mind.
- Running `cargo check`/`clippy`/targeted tests after every discrete change
  rather than batching - every regression this session (the `_unknownSecretType`
  test-state leak, the totp-ipc test suite's missing `st.vaultOpen`, the
  composite masking test's wrong assumption about `extra_vars`' pre-existing
  opt-in secret flag) was caught within one tool call of being introduced.

**Didn't work / watch for:**

- The full `npx vitest run` reported "1 failed | 1156 passed (1157)" with
  **exit code 0** - the background wrapper's own exit code is not a
  substitute for reading the summary line. Chased it: `tests/modals.test.ts`'s
  "TYPE_CONFIG covers every secret type" asserted the exact 8-member key set,
  which this session's `composite`/`bundle` additions legitimately grew to
  10 - not flakiness, a real assertion this session needed to update and
  initially missed because a _targeted_ run of `tests/modals.test.ts` alone
  (run several times earlier in the session, before the composite work) had
  passed, and the composite-specific tests were checked with their own
  targeted runs that never happened to include this particular `it`. Fixed;
  full suite green after. **Lesson: a targeted re-run after a change is not
  the same guarantee as the specific test file that would have caught it -
  run the full suite, not just the file you think you touched.**
- Piping a long-running command straight through `tail -N` as part of the
  backgrounded command itself throws away everything before the last N
  lines permanently - when a failure needs its stack trace, redirect to a
  file and `grep`/`tail` the file afterward instead of baking `| tail` into
  the backgrounded command.

## Notes for whoever picks this up

- `src/ts/composite.ts` and `vault-core/src/composite.rs` are meant to be
  read side by side - every function has a same-named counterpart, and the
  module doc comments cross-reference each other. If you change one, open
  both.
- The bundle fields (`bundle_id`, `bundle_slot`, `bundle_order`,
  `bundle_primary`) exist in `types.ts` with full doc comments describing the
  eventual design, but **nothing reads or writes them yet** except that a
  `bundle`-typed entry can be created and saved (as an otherwise-inert
  `env_var`-shaped entry, per the design's own B11 "older builds" fallback -
  which is currently _every_ build, including this one's UI).
- `refreshCompositePreview` and `refreshRequiredMarker` (A5) are both wired
  through `dynamicSecretFields`, which now does more than its name suggests
  (type-driven field visibility _and_ two live previews). If it grows a
  fourth concern, consider splitting it - the function was already long
  before this session.
