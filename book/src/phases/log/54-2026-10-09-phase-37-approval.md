## 1. The problem

Nodes (phase log 51) let automation change production: edit the vault and a node writes the file on a live host within a beat. phase log 23 T5: put a human between the render and the apply, bind the yes to the exact bytes (approving "a change to nginx" rather than "these bytes" is a time-of-check/time-of-use hole), make the diff readable (approval fatigue is the real failure mode), and let staging apply freely while production requires a tap.

## 3. Decisions and rejected alternatives

1. **A request is for `(node, target, sha256)`, nothing coarser.** This is the TOCTOU answer: if the vault changes while a request waits, the rendered hash changes, `usable_approval` finds nothing for the new hash, and a new request opens (test `an_approval_is_for_the_bytes_that_were_shown…`). A consumed or expired request for the same bytes (a revert) does not cover a later push (`a_spent_request_for_the_same_bytes_does_not_cover_a_later_push`).
2. **The hub withholds the content**, it does not send it and ask the node to hold it. A pending request produces a `pending` note and no `Push` action, so the bytes are not on the wire or on the host until a yes exists.
3. **The yes is signed, and the node can demand it independently.** Policy on the hub (`approval = required`) stops the hub from sending. `require_approval = true` in the node's own config makes the node refuse anything without a valid signed approval, so a hub bug, a policy change, a sub-user write path or a replayed action cannot push there. The token binds node, target, hash, approver, expiry and nonce. Rejected: an unsigned flag in the push (a hub bug could set it).
4. **The signing seed lives in the vault's encrypted `vault_meta`**, like the unique-ID registry's secrets, not in `nodes.json`: a copy of the registry file is not enough to forge an approval, and the key exists only while the vault is open, which is also when a push can be made.
5. **Trust on first use for the hub's approval key, over the already-pinned TLS channel**, rather than a key delivered at enrollment: enrollment can happen while the hub is locked and has no key to give. A different key later is a hard error that stops the run loop (`denied`), re-enrolling is the fix. A node that has not yet seen the key refuses approval-requiring pushes (test).
6. **Spend the nonce on a write, not an attempt.** A failed validate restores the old file and the hub will push again next beat with the same approval; burning the nonce on the attempt would make every retry fail with "already used".
7. **One request audit row per request** (`first` pass only, and only when the request is new), because a held push is re-evaluated every beat; a row per beat would be the heartbeat-in-the-chain mistake again (test: five beats, one row).
8. **Review is the history's diff.** The request stores snapshot numbers, never content; Phase 35's masked diff is what the human reads (fingerprints, so a rotated key shows as a changed fingerprint). `--reveal`/Reveal is deliberately not the default for approval. The question includes the hash so the thing approved is the thing on screen.
9. **Not built (ADR-0143):** an approval signed on the owner's own device (a compromised hub can mint approvals; what holds is that bugs and replays cannot, and that the owner's yes is for exact bytes); a per-target hub policy (per node is enough: staging `none`, production `required`; the target-level control is the node's own setting); a push notification when something is held.

## 5. Traps

- `record_beat` takes `unix_now()` for approval lifetimes, not the caller's clock; tests that need a lapsed approval use the explicit `now_secs` arguments of `usable_approval`/`decide`.
- The approval request is created from `process()` **before** `record_beat`; if you reorder them the first beat after a change will report `pending` instead of `awaiting_approval`.
- `usable_approval` also requires the node to be active: revoking a node withdraws its outstanding approvals.
- A hub that is locked has no key and no vault: it sends no pushes at all, approved or not.
- `approvals-seen.json` is only the replay ring for tokens that were _used_; deleting it re-opens replay of tokens that have not yet expired (at most an hour).
