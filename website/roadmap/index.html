UnENVerse roadmap to 1.0.0

Plan for 18 October 2026 to October 2027, ending in 1.0.0. It is a statement of intent, not a promise: dates move when a defect, a security finding or a dependency change takes priority. Compatibility and security work always goes before new features.

Where it stands Done

Phases R00 to R09 are done: baseline, security hotfixes, CI release gating, dependency modernisation, the shared unv-app layer, transactional SQLCipher migrations with local recovery, SFTP backups with retention and restore drills, the metadata and lifecycle core, the lossless config migration core, and full-fidelity import from Bitwarden, 1Password and KeePass. The website (W1), the CLI half of signed updates (R26) and a behaviour-test round across Rust and TypeScript (Phase 56, 0.56.0) are also done.

The year, by quarter

  1. October to December 2026: foundations

    In progress

    • R21 Compatibility contract and catalogue URL. Publish what integrators can rely on (CLI output, exit codes, file formats), test it, and fix the catalogue URL defect.
    • R20 Delete, revoke, forget, rekey. Every destructive verb does exactly what the UI says; "forget" purges old values from local history; the master password can be changed.

    Release

    1.0.0 ships when the criteria at the end of this page are all true.

After 1.0.0: the agent-safety lane

In October 2026 ProjectDiscovery showed that a small fine-tune of an open model (about $8 of GPU time for the run) can pass every clean test and still, on a trigger phrase, make a coding agent fetch a script that posts every .env file and SSH key in the working directory to a stranger's server. No benchmark or scanner can tell such a model from a clean one, so the defence is to limit what the agent can read and reach. UnENVerse is not a sandbox and cannot detect a backdoored model, but it can make the stolen thing worthless and the theft visible. Five phases are planned after 1.0.0:

  • Ref-only project files. unv env --refs writes a file of ${refs}, not values, and a migrate command replaces a plaintext .env with it.
  • Per-command secret release. A secret is released only to the commands it was bound to, so a model-written shell line gets nothing.
  • An SSH agent. Keys are served over the agent protocol and never sit as files under ~/.ssh.
  • Canary entries. Decoy credentials planted where an attacker looks first, with an alert when one is used. This detects theft; it prevents nothing.
  • Sandboxed exec. An opt-in launcher with filesystem and egress limits that fails closed on a platform that cannot enforce them.

Every numbered phase, done and planned, is listed in the phases section of the documentation.

Criteria for 1.0.0

1.0.0 ships when every item below is true, and not before.

  1. Every phase above is complete, or removed from this page with the reason.
  2. Test coverage is the reachable maximum for Rust and TypeScript, measured in CI, with each unreachable line (platform-only or defensive code) listed. Tests assert behaviour the documentation promises; the number is only a map.
  3. The independent security assessment is done and its findings fixed or documented in SECURITY.md.
  4. Fuzz targets run as a release gate, and a release builds reproducibly.
  5. Release tags are signed, and releases carry signatures, provenance and SBOMs.
  6. The OpenSSF Best Practices Passing and Baseline badges hold, and Silver and Gold are met wherever one maintainer can meet them (see below).
  7. macOS is shipped only if it is built, tested and documented.
  8. A vault written by any 0.x release since 0.42 opens, with a backup kept first.

OpenSSF Silver and Gold

Some criteria need more than one person: a bus factor of two, two unassociated significant contributors, two-person review and a second holder of the release keys. The plan is to keep the project open to a second maintainer (see CONTRIBUTING.md and the good first issue label) rather than to claim those criteria early. Everything else is in the plan above: source headers, signed tags, reproducible builds, fuzzing in the release gate and the coverage targets.

What the project will not do

  • Charge for it, gate a feature behind payment, or require a cloud service.
  • Run an always-on daemon: scheduled work runs while the desktop app is open and the vault is unlocked, and the docs and UI say so.
  • Claim macOS support, or any integration, before it is built and tested.
  • Let automation satisfy a human-approval requirement.
