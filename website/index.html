UnENVerse is an encrypted vault on a machine you control, with a desktop app, a command-line tool (unv) and an optional server for your team. It stores the secrets and also builds the config files that use them, so a rotation reaches every file by itself.

Built for three jobs

Self-hosted, with nothing of yours on our side

The vault is one encrypted database on your own disk, locked with a key derived from your master password. There is no UnENVerse server and no account. Run it on a laptop, or put unv-server on a machine you control and point the desktop app and the CLI at it. An official Docker image is published.

  • Self-signed certificates are pinned, never silently trusted.
  • Encrypted backups and recovery packages go to a disk, a NAS or SFTP.

AI agents and scripts use secrets, never read them

The unv CLI prints every stored value as a fingerprint. To use a secret, unv exec starts a program with it in its environment and unv render writes it into a file, so the agent running the show never reads it. Equal fingerprints mean equal secrets, so it can still spot drift and duplicates.

  • Stable exit codes, and unv describe returns the whole command set as JSON.
  • A vault-wide export to the terminal is refused, not masked.

Teams, with their own logins and limits

Run unv-server and give each person a named user, their own API tokens and an optional second factor. Roles are classes, and permissions are rules such as tag:llm OR tag:ci, with a live count of the entries a rule matches. Simultaneous edits merge per entry.

  • Every add, update, delete and read goes into a hash-chained audit log.
  • Nodes on your servers can require an approval before a config changes.

What sets it apart

It knows what each secret is for

A config points at a vault entry (${GitHub/token}). The value lives in one place, so a rotation reaches every wg0.conf, Compose file and .env built from it. Most vaults store a password and hand it back.

Agents use secrets, never read them

Every value prints as a fingerprint by default. unv exec and unv render put the real one into a process or a file and nowhere else. Exit codes and unv describe give an agent the whole contract as JSON.

A time machine for config

Every save snapshots each rendered config with secrets masked. A rotation shows as a changed fingerprint. After a compromise, blast radius names the exact credentials a machine saw and the one command to rotate them.

Deploys that need your yes

Node agents on your servers watch a file and, only where you allow it, receive the new one transactionally. Production can require an approval signed on your own machine, bound to the exact bytes.

Proof, not promises

The audit log is hash-chained, so tampering breaks it. unv doctor checks the vault without changing it. Releases are signed with Sigstore. There is no UnENVerse server, so nothing of yours sits with us.

One app and one CLI, identical

Whatever the desktop app can do, unv can do, and the reverse. Start alone on a laptop, then add unv-server with named users, classes and a permission language when a team needs it.

One workflow, end to end

Rotating one credential that several configs share:

  1. Edit the entry once. Every config that references it, such as an .env file, a WireGuard interface or an nginx block, renders from the new value. Compose files keep ${VAR} for Compose itself to fill in.
  2. Read the diff. Config history shows each file's before and after, with the secret masked.
  3. See what to touch. The blast-radius report names the machines that held the old value.
  4. Apply on purpose. A node agent on each host can observe a file, and, if you allow it, receive the new one, with an optional human approval bound to the exact bytes.

Shipped parts: references and rendering, config history, blast radius, node agents with approval. Node agents install on Linux (systemd).

Honest limits

  • It is not a hosted service. You run it and you back it up.
  • A forgotten master password cannot be recovered. Keep the .vaultbak backup and the vault.salt file safe.
  • It is not a browser autofill extension.
  • macOS builds are not published yet.
  • The node agent is documented for Linux with systemd.
